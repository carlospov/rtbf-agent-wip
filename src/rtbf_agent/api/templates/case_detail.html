{# Case detail / event audit trail template (issue #55). Every piece of display text below is a double-brace interpolation of a value that rtbf_agent.api.case_detail.case_detail already resolved via I18nProvider.translate() -- this file itself contains no hardcoded English (or any other language's) text, per R23. tests/api/test_case_detail.py scans this file mechanically to enforce that: everything outside double-brace interpolations, percent-brace control blocks, this comment, and HTML tags/attributes must be pure whitespace. event.detail_items' "label"/"value" pairs are also interpolations, not literals authored here -- for document-kind events they come from a fixed hash/size/extension allowlist (case_detail.py's _document_detail_items()); for every other kind they are the event's own free-form audit data (e.g. a drafted request's subject/body), never text this template invents. Approve/reject forms (issue #67): plain HTML
POSTs to api/approval.py's routes, only rendered when can_approve is true (the case is eligible to send -- Draft ready and not yet approved, or Requires human action with a pending preview draft, the drafting-is-a-preview redesign) -- no client-side state management, matching api/app.py's "server-rendered HTML, not an SPA" decision. Follow-up confirm/dispute forms (automated-case-loop rework, Phase 5): same plain-HTML-POST shape, posting to api/followup.py's routes, only rendered when pending_followup is set (an unconsumed classified reply is actually pending -- only ever REJECTION now; see case_detail.py's module docstring). pending_followup.reasoning is the agent's own audit data (already i18n-labeled), never text this template invents. Reopen form (mitigating control for follow_up()'s CONFIRMATION auto-close): same plain-HTML-POST shape, posting to api/followup.py's reopen route, only rendered when can_reopen is true (the case is actually Deletion confirmed). Additional-info forms (automated-case-loop rework, Phase 5): a text and a file-upload , posting to api/document.py's routes, only rendered when can_provide_additional_info is true (the case is actually in Requires human action). additional_info_summary is the latest additional_info_requested event's own reasoning, not text this template invents. pending_additional_info_text (maintainer live-UX feedback) is the freshest text answer already on record for the current round -- shown above the textarea (which it also pre-fills) since the textarea itself always renders empty on a fresh page load regardless of what was submitted earlier, and without this there was no way to confirm what note a subsequent "Draft" click would actually use. "Draft" form (drafting-is-a-preview redesign, superseding issue #117/#119's fused "this round is ready" draft+send button -- see followup.py's module docstring): a third, visually-separated in the same block (dashed top border, bold button -- deliberately not styled like the two recording forms above it), posting to api/document.py's additional-info/draft route (followup.draft_additional_info_response()). Composes a preview only -- case.state stays Requires human action -- so the edit/approve/reject section below (can_edit_draft/can_approve) appears right on this same page once a draft exists, without the case ever appearing to change kanban column. Document vault section (issue #111): alongside the upload form above, a checkbox list of existing vault documents (vault_documents, each already i18n-safe -- "label" is either the document's own human-supplied label or a "document-{id}" fallback built in case_detail.py, never free text authored here), posting to api/vault.py's select-documents route. Links to /vault (api/vault.py's own browse/delete page) for full vault management. Each document's own "selected" flag (maintainer live-UX feedback, LLM-drafted-replies extension) -- whether followup.selected_documents() currently counts it as this round's actual selection, the same read cli.run_once()'s send loop uses to decide what gets attached -- pre-checks its checkbox and shows vault_selected_badge_text next to it, so re-opening this page after selecting shows what's really going to be sent, not always-unchecked boxes regardless of prior selection. Jurisdiction/drafting-language override forms (no-prompt-at-creation reversal): two independent plain-HTML-POST forms (R22 -- never a package deal), posting to api/case_overrides.py's routes, only rendered when can_edit_case_overrides is true (the case is still Discovered, before agent_loop._classify() locks these fields in) -- each pre-filled with the current, possibly-empty value. The case summary above always shows both fields' current value (or blank) regardless of editability. Recipient confirmation form (follow-up to #94): same plain-HTML-POST shape, posting to api/recipient.py's route, rendered while can_confirm_recipient is true. The input is pre-filled with case.recipient_email if already set, else recipient_suggestion.recipient if a proposal exists, else empty -- submitting unedited accepts the suggestion, editing first overrides it. recipient_suggestion's reasoning/sources are the LLM's own audit data (already i18n-labeled by the two labels around them), never text this template invents. Each event is a native
